# sleep-secret 与眠伴 0.3.2 对比

## 2026-11-18 更新

眠伴 0.3.3 在 Android 增加录音音质选择。节省空间档为 24 kbps AAC，清晰档为 48 kbps AAC，按编码参数分别约占 11 和 22 MB/小时。Sleep Secret v2.25.1 的 16 kHz 单声道 PCM16 WAV 约占 115 MB/小时。只保存鼾声时，两边都按实际保留片段的时长占用空间。

API 35 模拟器用相同的 8 秒合成音频测试，两档 M4A 分别为 27,351 和 51,264 字节，均通过轨道读取测试。该测试检查编码与存储，真实卧室录音的听感需用手机比较。

### 同源片段识别对照

使用 Sleep Secret v2.25.1 的四个鼾声夹具及雨声、鸡鸣，逐份提供原始振幅、衰减 12 dB 和衰减 24 dB 的 PCM。表中每个数字是命中鼾声的 3 秒区块数，按「原始／−12 dB／−24 dB」排列。YAMNet 沿用眠伴的判定阈值，区块中任一完整的 0.975 秒窗判为鼾声即命中。CED-tiny 按上游映射取组内最高分并判定得分最高的类别。两边均取完整的 3 秒区块，比较分类环节。

| 音频 | 区块数 | YAMNet | CED-tiny |
| --- | ---: | --- | --- |
| 频带受限鼾声 | 10 | 3 / 4 / 6 | 10 / 10 / 10 |
| `snore_01` | 1 | 1 / 1 / 1 | 1 / 1 / 1 |
| `snore_02` | 1 | 1 / 1 / 1 | 1 / 1 / 1 |
| `snore_05` | 1 | 0 / 0 / 0 | 1 / 1 / 0 |
| 雨声 | 1 | 0 / 0 / 0 | 0 / 0 / 0 |
| 鸡鸣 | 1 | 0 / 0 / 0 | 0 / 0 / 0 |

桌面 CPU 单次模型推理中位数约为 0.82 ms 和 14.27 ms，分别对应 0.975 和 3 秒模型窗，运行时分别是 LiteRT 和 ONNX Runtime。真机整晚功耗需要结合采集和编码测量。公开夹具数量少，且上游用 CED-tiny 参与夹具筛选。衰减模拟静音量变化，真实距离还会改变频响和信噪比。0.3.3 沿用 YAMNet，CED-tiny 是优先使用独立卧室标注录音验证的候选。

复现时从 [v2.25.1 模型目录](https://github.com/14790897/sleep-secret/tree/v2.25.1/app/assets/models) 取得 `ced-tiny.onnx` 和 `sleep_class_map.json`，从 [测试音频目录](https://github.com/14790897/sleep-secret/tree/v2.25.1/app/assets/testdata/real) 取得音频。CED 模型 Git blob 为 `1b462270c00e8a407a591ae95ebad5c77504bc1b`。在现有模型评测环境中安装 `onnxruntime`，运行 `python models/compare_ced.py --ced ced-tiny.onnx --class-map sleep_class_map.json snore_05.wav`。样本许可证及筛选说明见 [v2.25.1 第三方声明](https://github.com/14790897/sleep-secret/blob/v2.25.1/THIRD_PARTY_NOTICES.md)。

## 2026-11-13 对比记录

核对日期为2026-11-13，目标是决定后续使用与开发路线。

本地基线为已交付的眠伴0.3.2。新用户流程建议尚未成为发布功能，本轮中途开始的草稿已独立保存到 `.tmp/first-use-wip/`，本表不计入这些草稿能力。

对方源码固定在 `5b95fa3a9c03da6a08ce8f73d2d068bf74304d6c`。最新发行版为v2.23.1，发布于2026-11-12。该提交比发行版多一个文档提交，差异为README及使用指南。已核对源码、文档、发行记录和GitHub CI结果，本轮没有运行对方应用、重跑其测试或进行真机准确率与耗电评测。

## 判断

sleep-secret已有完整的录音、事件报告、波形回放、趋势和导出导入链路，值得先作为候选主线试用。更有效的下一步是确认其采集可靠性及个人录音识别表现，再决定直接使用或向上游贡献所缺功能。

现有工程可作为功能与模型对照。若转到sleep-secret，主要工作将集中在压缩音频与全程保存、最近记录的逐项比较和分布对照、多供应商AI，以及异常中断恢复。产品方向与上游一致时，适合拆成小范围PR协作。

音频体积按 `16000 × 2字节/秒` 与 `24000 bit/秒 ÷ 8` 推算。对方20分钟片段约38.4 MB，同样时长24 kbps音频约3.6 MB。实际采用压缩格式需要同时处理播放器、导出导入和历史WAV兼容。

## 需要在采用前验证的三个问题

1. **异常中断恢复**。`recording_repository.dart` 的主流程在 `stop()` 后调用 `insertSession()`。实时计数主要在内存中发布，未找到录制中定期会话检查点。因此强杀、进程被回收或断电后的报告恢复能力是源码审查发现的风险，仍需实测。片段已经写出也不等于完整会话元数据可恢复。
2. **录音中播放音乐及锁屏**。v2.23.1已经合入将 `audioInterruption` 设为 `none` 的修复，不能把较早PR描述直接当成最新版仍存在的缺陷。电话、权限撤回、系统静音、厂商省电策略及整夜锁屏还要用实际手机验证。
3. **准确率证据**。对方第三方声明说明测试素材会先按同一模型打分筛选，这些样本可以验证管线连通。个人弱鼾、风扇、空调与远距离声音的泛化表现需要独立标注样本比较。模型参数规模、类别数和单元测试数量不足以给出谁更准的结论。

对方WebDAV凭据目前保存在应用私有SQLite中，隐私文档明确说明未加密。若启用同步，需要把这项存储选择纳入评估。本项目AI密钥使用系统安全存储，两类凭据的实现不能简单等同。

## 建议路线

先从最新版现成应用试用开始，确认个人手机上的弱声回听、误报情况、锁屏整夜记录、音频焦点及存储占用。模型比较应给两套模型输入同一份音频，并独立标注鼾声与非鼾声片段。

通过核心验证后，再按需求优先级贡献小范围改动。第一组是压缩存储及可选全程保留，第二组是最近一次逐项对比和双记录分布，第三组是人工纠正和异常中断恢复。AI可作为独立可选模块讨论，尤其需要与上游的本地处理定位协调。

本项目JSON/AAC与对方SQLite/WAV不是同一种归档格式，数据迁移需要单独验证。GPL-3.0为对方项目许可证，后续修改与分发应据该许可证规划，具体文本见下方来源。
